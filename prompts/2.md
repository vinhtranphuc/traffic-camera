## 3. ROLE HIERARCHY & PERMISSIONS

```
SystemAdmin
    └── SuperAdmin (manages Admins + Customers)
            └── Admin (manages assigned Customers)
                    └── Customer (end user)
```

### 3.1 Customer
- Login: email/password (OTP via email) OR Google OAuth OR Zalo OAuth
- Manages their own cameras (add/edit/delete/group)
- Views live streams, detection history, dashboard
- Receives real-time notifications
- **Camera source changes require Admin approval before activation**

### 3.2 Admin
- Login: username/password only
- Manages cameras for assigned customers (add/edit/group)
- Approves/rejects customer camera requests
- Can create customer accounts (username/password type)
- Can temporarily lock customer accounts
- Dashboard: filter by their assigned customers or all customers they manage
- **Admin's own cameras do NOT require approval**

### 3.3 SuperAdmin
- Login: username/password only
- Manages Admin accounts + assigns customers to Admins
- Can do everything Admin can do
- System resource monitoring: which cameras/accounts consume most resources
- Dashboard: filter by one user, multiple users, or all
- Camera connection status overview (offline, error, active)

### 3.4 SystemAdmin
- Login: username/password only
- Manages SuperAdmin accounts only (cannot touch Admin or Customer)
- System-wide configuration:
  - Enable/disable video source types (stored in DB, effective immediately without redeploy)
  - Configure Zalo OAuth / Google OAuth credentials (stored in DB, effective immediately without redeploy)
  - Configure Firebase (API key, project ID, app ID, messaging sender ID, auth domain, storage bucket, etc.) (stored in DB, effective immediately without redeploy)
- Can temporarily block SuperAdmin login

## 4. CAMERA APPROVAL WORKFLOW

This is a critical business rule. Implement it precisely:

```
Customer adds/edits camera (source-related fields)
    → Camera status = PENDING_APPROVAL
    → Admin receives real-time notification
    → Admin clicks notification → goes to approval detail page
    → Admin APPROVES → camera becomes ACTIVE → Customer notified
    → Admin REJECTS (with reason) → camera stays REJECTED → Customer notified
    
Rules:
- REJECTED cameras still appear in Customer's camera list (with REJECTED badge + reason)
- REJECTED cameras cannot stream or detect
- Admin adding camera for Customer = no approval needed, immediately ACTIVE
- Admin editing own cameras = no approval needed
- Approval history must be stored and visible
```

## 5. CAMERA MANAGEMENT FEATURES

### 5.1 Supported Video Sources
Each source type has different connection fields:
| Source Type   | Connection Fields                          |
|---------------|--------------------------------------------|
| RTSP          | URL, username, password, port              |
| HTTP/MJPEG    | URL, auth headers                          |
| WebRTC        | Signaling URL, ICE config                  |
| USB/Local     | Device path/index                          |
| HLS           | M3U8 URL                                   |

SystemAdmin controls which source types are enabled globally.

### 5.2 Camera CRUD
- Add/edit/delete cameras with validation per source type
- Pin camera on map (Leaflet, lat/lng stored in DB)
- Camera groups: create groups, assign cameras, manage by group
- Camera status: PENDING_APPROVAL | ACTIVE | REJECTED | OFFLINE | ERROR | STOPPED

### 5.3 Camera Controls
- Start/Stop camera
- Schedule: configure time windows for automatic start/stop (cron-based)
- Per-camera detection toggles:
  - Detect vehicles (car / truck / bus / motorcycle individually toggleable)
  - Detect persons
  - Detect license plates
  - Detect traffic violations (configurable per camera)
- ROI (Region of Interest) configuration:
  - Draw polygon/rectangle on live frame via canvas
  - Multiple ROI zones per camera
  - Each zone can have different detection rules

### 5.4 Live View
- Live stream in camera list (popup modal)
- Live stream in camera detail page
- Full-screen multi-camera grid view
  - User can drag/resize tiles (flexible layout, not fixed grid)
  - Remember layout preference per user

### 5.5 Detection History
- Search by: camera, camera group, detection type, time range, license plate text
- Paginated results (cursor-based pagination)
- Display: thumbnail, timestamp, detection type, camera name, confidence score
- Export to CSV
- Backend stores events in real-time with MinIO snapshot storage

## 6. NOTIFICATIONS

### 6.1 Triggers
| Event                              | Who gets notified |
|------------------------------------|-------------------|
| Customer adds/edits camera (source)| Admin             |
| Admin approves/rejects camera      | Customer          |
| Admin modifies customer's data     | Customer          |
| Camera goes offline/error          | Camera owner      |
| System admin actions on SuperAdmin | SuperAdmin        |

### 6.2 Implementation

**Delivery channels (dual-channel approach):**
- **Firebase Cloud Messaging (FCM)**: primary push notification channel for all events
  - Backend uses Firebase Admin SDK to send FCM messages
  - Frontend registers FCM token on login and stores it in DB (per device, per user)
  - FCM token refreshed automatically via Firebase SDK and re-synced to backend
  - If Firebase config is not yet set up by SystemAdmin → fall back to WebSocket only
- **WebSocket (STOMP over SockJS)**: in-app real-time channel for users currently online
  - Ensures instant UI update (toast, bell badge) even when FCM delivery is delayed

**Storage & state:**
- All notifications persisted in DB regardless of delivery result or user's setting
- User setting: toggle FCM push per event type (bell icon always shows unread count)
- Notification bell: dropdown with read/unread state, mark all as read
- Toast alert for incoming real-time events (WebSocket)

**FCM message structure:**
```json
{
  "title": "Camera approval required",
  "body": "Customer X added a new camera pending your approval",
  "data": {
    "type": "CAMERA_APPROVAL_REQUESTED",
    "targetId": "camera-uuid",
    "redirectUrl": "/admin/approvals/camera-uuid"
  }
}
```
- `redirectUrl` used by frontend to navigate on notification click

## 9. AI/DETECTION PIPELINE INTEGRATION

> Note: The AI pipeline runs separately (Python). Backend exposes REST endpoints to
> receive detection events from the AI service. Frontend consumes these via WebSocket.

Backend must:
- Accept POST `/api/internal/detections` from AI service (secured with internal API key)
- Store: camera_id, timestamp, object_type, confidence, bounding_box JSON, snapshot_url (MinIO)
- Emit WebSocket event to relevant user subscriptions
- Respect per-camera detection toggle settings (filter at ingest)
